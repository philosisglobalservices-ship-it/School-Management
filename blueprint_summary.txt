1. Product Scope and Principles
1.1 Vision
Provide a centralized, secure platform for school administration, student records, academic assessment, attendance, communications, and reporting. Head Teachers receive broad school-level oversight; teachers are limited to assigned responsibilities; students can view their own authorized information but cannot edit official scores; parents can view records only for verified linked children.
1.2 In Scope
Identity, authentication, first-login password replacement, MFA for privileged accounts, account recovery, sessions, and access reviews.
School configuration, academic sessions, terms, classes, subjects, staff, students, guardians, enrolments, and teacher assignments.
Assessment setup, score entry, submission, review, approval, publication, controlled correction, and report cards.
Student attendance, timetables, announcements, parent/student portals, notifications, reporting, audit and security monitoring.
Optional fee-management module with separate permissions and reconciliation controls.
Responsive web UI, documented APIs, migrations, automated tests, deployment and recovery operations.
1.3 Out of Scope Unless Approved
Payroll, full HR, learning management authoring, video conferencing, biometric attendance hardware, payment processing, transport, library, and inventory.
Offline editing of official scores; mobile apps beyond responsive web; cross-school data sharing.
Automated high-stakes grading decisions without human review.
1.4 Non-negotiable principles
Deny by default; grant least privilege; enforce authorization server-side on every request and background job.
School/tenant, class, subject, student relationship, record state, and effective dates are part of authorization decisions.
A student cannot create, update, approve, or publish official scores.
Parents cannot access a child until the relationship is verified and active.
Published results are versioned and never silently overwritten or physically deleted through normal workflows.
Critical actions are attributable and audit records are protected from ordinary application-user modification.
Fail closed for authorization and sensitive operations; preserve data integrity under retries, concurrency, and outages.

2.2 RBAC + ABAC decision contract
authorize(subject, action, resource, environment):
  if subject is unauthenticated or session is revoked/expired: DENY
  if account is disabled, locked, or must change password and action is not allowed in that state: DENY
  if resource.school_id != subject.active_school_scope: DENY
  if no active role grants action: DENY
  if action requires attributes:
      verify effective assignment, relationship, ownership, resource state,
      academic session, time window, and any approval/separation-of-duty rules
  if resource is published/finalized and action is a mutation:
      require explicit correction workflow permission
  emit security event for policy-defined denied/high-risk actions
  ALLOW only when all applicable checks pass
The policy engine must be centralized or consistently shared by all services. Never rely on frontend route guards, hidden controls, client-supplied role names, or untrusted tenant IDs.

5.2 Entity conventions
Primary keys: UUID. Timestamps: timestamptz stored in UTC. UI displays school-configured timezone.
Every school-owned row has school_id; composite foreign keys or equivalent constraints must prevent cross-school references.
Use created_at, updated_at, created_by, updated_by where meaningful; audit log remains the authoritative history for critical changes.
Use status enums/check constraints with explicit state transitions; do not permit arbitrary state strings.
Use optimistic concurrency via version integer or ETag for mutable records.
PII is minimized; sensitive data is encrypted where warranted and never copied to logs.

6. PostgreSQL Reference Schema
The following reference DDL covers the core entities and key constraints. It is a baseline migration, not a substitute for environment-specific migration review, row-level security decisions, or full data-retention policies. Use a migration tool and apply changes through reviewed version-controlled migrations.
CREATE EXTENSION IF NOT EXISTS pgcrypto;
 
CREATE TABLE schools (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  slug text NOT NULL UNIQUE,
  name text NOT NULL,
  timezone text NOT NULL DEFAULT 'Africa/Lagos',
  status text NOT NULL CHECK (status IN ('active','suspended','archived')),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
 
CREATE TABLE users (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  email text,
  phone_e164 text,
  password_hash text NOT NULL,
  status text NOT NULL CHECK (status IN ('invited','active','locked','suspended','disabled')),
  must_change_password boolean NOT NULL DEFAULT true,
  failed_login_count integer NOT NULL DEFAULT 0 CHECK (failed_login_count >= 0),
  locked_until timestamptz,
  mfa_enrolled_at timestamptz,
  last_login_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  CHECK (email IS NOT NULL OR phone_e164 IS NOT NULL)
);
CREATE UNIQUE INDEX users_school_email_uq
  ON users (school_id, lower(email)) WHERE email IS NOT NULL;
CREATE UNIQUE INDEX users_school_phone_uq
  ON users (school_id, phone_e164) WHERE phone_e164 IS NOT NULL;
 
CREATE TABLE roles (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid REFERENCES schools(id),
  code text NOT NULL,
  name text NOT NULL,
  is_system boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (school_id, code)
);
CREATE TABLE permissions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  code text NOT NULL UNIQUE,
  description text NOT NULL,
  risk_level text NOT NULL CHECK (risk_level IN ('low','medium','high','critical'))
);
CREATE TABLE role_permissions (
  role_id uuid NOT NULL REFERENCES roles(id),
  permission_id uuid NOT NULL REFERENCES permissions(id),
  effect text NOT NULL DEFAULT 'allow' CHECK (effect IN ('allow','deny')),
  PRIMARY KEY (role_id, permission_id)
);
CREATE TABLE user_roles (
  user_id uuid NOT NULL REFERENCES users(id),
  role_id uuid NOT NULL REFERENCES roles(id),
  school_id uuid NOT NULL REFERENCES schools(id),
  valid_from timestamptz NOT NULL DEFAULT now(),
  valid_until timestamptz,
  granted_by uuid NOT NULL REFERENCES users(id),
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, role_id, school_id),
  CHECK (valid_until IS NULL OR valid_until > valid_from)
);
 
CREATE TABLE students (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  user_id uuid UNIQUE REFERENCES users(id),
  student_number text NOT NULL,
  first_name text NOT NULL,
  middle_name text,
  last_name text NOT NULL,
  date_of_birth date,
  status text NOT NULL CHECK (status IN ('applicant','active','transferred','graduated','withdrawn','suspended')),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (school_id, student_number),
  UNIQUE (school_id, id)
);
 
CREATE TABLE guardians (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  user_id uuid NOT NULL UNIQUE REFERENCES users(id),
  first_name text NOT NULL,
  last_name text NOT NULL,
  relationship_label text,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (school_id, id)
);
CREATE TABLE student_guardians (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  student_id uuid NOT NULL,
  guardian_id uuid NOT NULL,
  status text NOT NULL CHECK (status IN ('pending','verified','revoked','rejected')),
  verified_at timestamptz,
  verified_by uuid REFERENCES users(id),
  valid_from date NOT NULL DEFAULT CURRENT_DATE,
  valid_until date,
  FOREIGN KEY (school_id, student_id) REFERENCES students(school_id, id),
  FOREIGN KEY (school_id, guardian_id) REFERENCES guardians(school_id, id),
  UNIQUE (school_id, student_id, guardian_id),
  CHECK (valid_until IS NULL OR valid_until >= valid_from)
);
 
CREATE TABLE staff (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  user_id uuid NOT NULL UNIQUE REFERENCES users(id),
  employee_number text NOT NULL,
  first_name text NOT NULL,
  last_name text NOT NULL,
  employment_status text NOT NULL CHECK (employment_status IN ('active','leave','suspended','terminated')),
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (school_id, employee_number),
  UNIQUE (school_id, id)
);
 
CREATE TABLE academic_sessions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  name text NOT NULL,
  start_date date NOT NULL,
  end_date date NOT NULL,
  status text NOT NULL CHECK (status IN ('planned','active','closed','archived')),
  UNIQUE (school_id, name),
  UNIQUE (school_id, id),
  CHECK (end_date >= start_date)
);
CREATE TABLE terms (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  session_id uuid NOT NULL,
  name text NOT NULL,
  sequence_no smallint NOT NULL CHECK (sequence_no > 0),
  start_date date NOT NULL,
  end_date date NOT NULL,
  FOREIGN KEY (school_id, session_id) REFERENCES academic_sessions(school_id, id),
  UNIQUE (session_id, sequence_no),
  CHECK (end_date >= start_date)
);
CREATE TABLE classes (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  name text NOT NULL,
  level text,
  stream text,
  status text NOT NULL CHECK (status IN ('active','inactive','archived')),
  UNIQUE (school_id, id),
  UNIQUE (school_id, name, stream)
);
CREATE TABLE subjects (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  code text NOT NULL,
  name text NOT NULL,
  status text NOT NULL CHECK (status IN ('active','inactive')),
  UNIQUE (school_id, code),
  UNIQUE (school_id, id)
);
CREATE TABLE enrollments (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  student_id uuid NOT NULL,
  class_id uuid NOT NULL,
  session_id uuid NOT NULL,
  start_date date NOT NULL,
  end_date date,
  status text NOT NULL CHECK (status IN ('active','completed','transferred','cancelled')),
  FOREIGN KEY (school_id, student_id) REFERENCES students(school_id, id),
  FOREIGN KEY (school_id, class_id) REFERENCES classes(school_id, id),
  FOREIGN KEY (school_id, session_id) REFERENCES academic_sessions(school_id, id),
  UNIQUE (school_id, id),
  CHECK (end_date IS NULL OR end_date >= start_date)
);
CREATE UNIQUE INDEX enrollments_one_active_student_session
  ON enrollments(school_id, student_id, session_id) WHERE status = 'active';
 
CREATE TABLE teacher_assignments (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  staff_id uuid NOT NULL,
  class_id uuid NOT NULL,
  subject_id uuid NOT NULL,
  session_id uuid NOT NULL,
  valid_from date NOT NULL,
  valid_until date,
  status text NOT NULL CHECK (status IN ('active','ended','revoked')),
  FOREIGN KEY (school_id, staff_id) REFERENCES staff(school_id, id),
  FOREIGN KEY (school_id, class_id) REFERENCES classes(school_id, id),
  FOREIGN KEY (school_id, subject_id) REFERENCES subjects(school_id, id),
  FOREIGN KEY (school_id, session_id) REFERENCES academic_sessions(school_id, id),
  CHECK (valid_until IS NULL OR valid_until >= valid_from)
);
CREATE INDEX teacher_assignments_scope_idx
  ON teacher_assignments(school_id, staff_id, class_id, subject_id, session_id, status);
 
CREATE TABLE assessments (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  class_id uuid NOT NULL,
  subject_id uuid NOT NULL,
  term_id uuid NOT NULL,
  title text NOT NULL,
  assessment_type text NOT NULL,
  max_score numeric(7,2) NOT NULL CHECK (max_score > 0),
  opens_at timestamptz,
  closes_at timestamptz,
  status text NOT NULL CHECK (status IN ('draft','open','closed','under_review','approved','published','cancelled')),
  version integer NOT NULL DEFAULT 1,
  created_by uuid NOT NULL REFERENCES users(id),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY (school_id, class_id) REFERENCES classes(school_id, id),
  FOREIGN KEY (school_id, subject_id) REFERENCES subjects(school_id, id),
  FOREIGN KEY (school_id, term_id) REFERENCES terms(school_id, id),
  CHECK (closes_at IS NULL OR opens_at IS NULL OR closes_at > opens_at)
);
 
CREATE TABLE scores (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  school_id uuid NOT NULL REFERENCES schools(id),
  assessment_id uuid NOT NULL,
  student_id uuid NOT NULL,
  score_value numeric(7,2),
  score_status text NOT NULL CHECK (score_status IN ('scored','absent','missing','exempt')),

8. Authentication and Account-Recovery Sequence Diagrams
8.1 First login / mandatory password change
sequenceDiagram
  actor User
  participant UI as Web UI
  participant API as Auth API
  participant IAM as Identity/Policy Service
  participant DB as PostgreSQL
  User->>UI: Submit credentials
  UI->>API: POST /auth/login
  API->>IAM: Verify credential + account status + rate limits
  IAM->>DB: Read user and password hash
  DB-->>IAM: User record
  IAM-->>API: Valid, must_change_password=true
  API->>DB: Create restricted session
  API-->>UI: Session + PASSWORD_CHANGE_REQUIRED
  UI->>API: POST /auth/change-password
  API->>IAM: Validate current session, password policy, CSRF, rate limit
  IAM->>DB: Store new Argon2id hash; clear flag; revoke temporary sessions/tokens
  IAM->>DB: Append audit event
  API-->>UI: 204 / next dashboard
  UI->>API: GET /me

8.2 Password recovery
sequenceDiagram
  actor User
  participant UI as Web UI
  participant API as Auth API
  participant IAM as Identity Service
  participant DB as PostgreSQL
  participant Mail as Email/SMS Provider
  User->>UI: Enter account identifier
  UI->>API: POST /auth/forgot-password
  API->>IAM: Rate-limit + normalize identifier
  IAM->>DB: Find eligible account internally
  IAM->>DB: Store hash of random single-use token with short expiry
  IAM->>Mail: Send generic recovery link if account eligible
  API-->>UI: 202 generic response (same wording for known/unknown account)
  User->>UI: Open recovery link and set new password
  UI->>API: POST /auth/reset-password {token,newPassword}
  API->>IAM: Hash token; check expiry, use status, policy, abuse controls
  IAM->>DB: Transaction: change hash, mark token used, revoke sessions, clear flag if policy permits
  IAM->>DB: Append audit/security events
  API-->>UI: 204 success; ask user to sign in
8.3 Login requirements
Generic login failure message; do not reveal whether username exists.
Rate-limit by account identifier and source/network signals; avoid permanent lockout that attackers can weaponize.
Use adaptive delay and risk-based step-up; alert on suspicious privileged-account attempts.
Cookie-based sessions: Secure, HttpOnly, SameSite appropriate to app; CSRF protection for state-changing requests.
Store only a hash of opaque session/reset tokens; never log tokens or passwords.
Force password replacement before allowing normal API routes; only login, logout, MFA, password-change, and recovery endpoints may be reachable in restricted state.
Re-check user status and relevant authorization on every request; invalidate cache entries when roles or assignments change.

10. API Standards and Endpoint Specifications
10.1 API conventions
Base path: /api/v1. JSON request/response; UTF-8; UTC ISO-8601 timestamps.
Authentication: secure server-managed session cookie; mutating requests require CSRF protection. If bearer tokens are selected instead, document rotation, audience, issuer, storage, and revocation strategy.
All responses include a request/correlation ID header; never include stack traces or secrets.
Use cursor pagination for large datasets; enforce maximum page size (default 50, hard maximum 200).
Use Idempotency-Key on operations where retries could duplicate side effects (bulk import, result publish, payment if later enabled).
Use If-Match/ETag or version fields for concurrent edits; return 409 on stale version.
Errors use stable machine-readable codes, safe messages, and optional field errors.
All endpoint examples are representative; implement the complete contract in OpenAPI 3.1 and validate it in CI.

11. Result Approval and Publication State Machines
11.1 State machine
DRAFT --teacher submits--> SUBMITTED
SUBMITTED --review begins--> UNDER_REVIEW
UNDER_REVIEW --reviewer returns--> DRAFT (reason required)
UNDER_REVIEW --reviewer approves--> APPROVED
APPROVED --publisher publishes--> PUBLISHED
PUBLISHED --authorized correction requested--> CORRECTION_PENDING
CORRECTION_PENDING --approver rejects--> PUBLISHED (original value retained)
CORRECTION_PENDING --approver approves--> PUBLISHED (new version + audit history)
DRAFT/SUBMITTED --authorized cancel--> CANCELLED (reason and audit required)

Enforce transitions in a domain service with transactional updates and a database-level version/locking strategy. Direct PATCH of workflow_status is prohibited. Publication should be idempotent and use a transactional outbox to avoid a published result without a corresponding notification job/audit event.

13.2 Incident-response lifecycle
1. Detect: monitoring creates an incident with timestamp, correlation IDs, affected service, and severity.
2. Triage: on-call confirms scope, impact, affected school/users/data, and whether the signal is genuine.
3. Contain: revoke sessions, disable affected accounts, pause exports/publication, isolate compromised component, or apply rate limits as appropriate.
4. Preserve evidence: retain relevant logs, deployment hashes, access events, and time window; restrict evidence access.
5. Eradicate: remove root cause, rotate exposed secrets, patch code/configuration, and close exploited access paths.
6. Recover: restore service/data from validated sources; verify academic record integrity and authorization tests.
7. Notify: follow the approved legal, regulatory, contractual, and school communication plan; do not improvise breach notices.
8. Review: document root cause, timeline, impact, corrective actions, owner, due date, and regression tests.

16. Deployment Architecture and CI/CD
16.1 Production topology
Internet
  -> DNS + TLS + WAF/rate limiting
  -> Load balancer / reverse proxy
  -> Web frontend (static/CDN or app server)
  -> API application instances (private network; horizontally scalable)
       -> PostgreSQL managed primary + standby / PITR
       -> private object storage (documents/exports)
       -> queue + background workers (notifications/reports/imports)
       -> optional Redis (cache/rate limits; never sole source of truth)
       -> centralized logs, metrics, traces, security events
  -> backup account/project with restricted write/delete privileges
16.2 Environment separation
Separate development, test, staging, and production accounts/projects, credentials, databases, and encryption keys.
No real student PII in developer laptops or test fixtures; use synthetic/masked data.
Production access is least privilege, MFA-protected, time-bounded, and audited.
Secrets are held in a managed secret store; never commit them to source control or bake them into images.
Private database and object storage; only necessary ingress exposed publicly.
Infrastructure is defined as code and reviewed like application code.
16.3 CI/CD pipeline gates
1. Pull request: formatting, linting, type checks, unit tests.
2. Dependency and license scan; secret scan; static application security testing.
3. Build immutable artifacts and generate software bill of materials (SBOM).
4. Database migration validation against an ephemeral database; backward-compatibility checks.
5. Integration tests, API contract tests, authorization-negative tests, and tenant-isolation tests.
6. Container/image scan and infrastructure-as-code policy scan.
7. Deploy to staging; smoke, end-to-end, accessibility, and performance regression tests.
8. Approval gate for production; canary/rolling deployment; health checks.
9. Post-deploy synthetic checks and automated rollback trigger if SLO/error thresholds are breached.
10. Record release ID, source commit, artifact digest, migration version, approver, and outcome.
16.4 Deployment safety
Use expand-and-contract database migrations: add compatible columns/tables, deploy compatible code, backfill, switch reads/writes, then remove old structures in a later release. Never rely on a destructive migration that cannot be rolled back safely. For score publication and schema changes, define explicit rollback and data-reconciliation procedures.

Appendix B. Example OpenAPI schema fragments
openapi: 3.1.0
info:
  title: ESAMS API
  version: 1.0.0
servers:
  - url: /api/v1
components:
  schemas:
    ErrorEnvelope:
      type: object
      required: [error]
      properties:
        error:
          type: object
          required: [code, message, requestId]
          properties:
            code: { type: string }
            message: { type: string }
            requestId: { type: string, format: uuid }
            fieldErrors:
              type: array
              items:
                type: object
                required: [field, code, message]
                properties:
                  field: { type: string }
                  code: { type: string }
                  message: { type: string }
    ScoreInput:
      type: object
      required: [studentId, scoreStatus]
      properties:
        studentId: { type: string, format: uuid }
        scoreStatus:
          type: string
          enum: [scored, absent, missing, exempt]
        scoreValue:
          type: [number, 'null']
          minimum: 0
        version: { type: integer, minimum: 1 }
      allOf:
        - if:
            properties:
              scoreStatus: { const: scored }
          then:
            required: [scoreValue]
        - if:
            properties:
              scoreStatus: { enum: [absent, missing, exempt] }
          then:
            properties:
              scoreValue: { type: 'null' }
Appendix C. Definition of Done
Acceptance criteria pass in CI and staging.
Authorization positive and negative tests pass, including resource ID substitution and school-scope tests.
Logs, metrics, audit events, and alerts are added for operationally important behavior.
Database migrations are reviewed, reversible where practical, and tested on representative data.
API contracts and UI documentation are updated.
No secret or sensitive student data is exposed in logs or error responses.
Feature flags, rollback, and support procedures are documented where relevant.
Product Owner and QA approve the user story; security review approves high-risk changes.
